# Djinn v0.1.2

v0.1.2 makes the Djinn orchestrator faster to act and clearer when it asks: the lead agent is now called the Djinn and is driven by Djinn by default—one headless batch per set of events, with its running batch and journal in the window, movable across agents, models and accounts, and speaking in the theme's tone—while `"leadDriven": false` in `settings.json` keeps the terminal lead with its safe read, Git and `djinn` commands pre-authorized. The Djinn plans tasks in conflict-free parallel graphs and keeps its operating notes built into the binary. Questions put every command you must run in a single code block at the top, preserve the initial question and every revision round across investigations, and give investigator workers web search, expanded read permissions, the project's model, and `--context-file`. Nothing Djinn started outlives it, errors and crashes land in its log with their stack, and the overview is now the flying carpet alongside the Hourglass for live metrics.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. One *Djinn*, the lead agent, splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.1.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.0) and [v0.1.1's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.1) describe all it does.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

## Djinn drives the lead by default, with a batch journal, seats, and theme tone

The lead agent is now called **the Djinn** across the window, and Djinn drives it by default without a terminal: when events wait (a task completed or failed, a merge, an answer, a message from **Write to the Djinn**, a restart), Djinn starts a fresh headless session for that batch in its own `lead/` folder, with the events whole, the briefs of the wishes they touch, the theme's tone (solar in light mode, mocking demon of the lamp in dark mode), and the journal of recent batches. Beside **Talk to the Djinn** on the flying carpet and at the top of a wish, the window shows the running batch (since when, events, cost) and opens the journal of past batches; each wish's **History** tab and `djinn lead journal` show the batches that touched that wish. The arrow beside **Talk to the Djinn** (or `djinn lead move`) moves the Djinn across agents (Claude Code or Codex), models and accounts (`djinn lead add-account`), and when a batch hits a subscription limit the attention bar offers each signed-in seat in one click.

Upgrading from a running terminal lead switches cleanly: the lead terminal is dropped, the window keeps the wish it showed, no waiting event is lost, and the journal starts with the next batch. Setting `"leadDriven": false` in `settings.json` goes back to the interactive lead terminal, with its safe `djinn`, `git` and read-only shell commands pre-authorized (`--allowedTools` on Claude Code, `djinn-lead.json` on Antigravity). Its operating rules live in built-in, read-only notes (`djinn lead notes`): it gives emoji prefixes to wish and azima titles, keeps notes factual, and plans tasks as a conflict-free parallel graph instead of a single sequential chain, adding `--after` only when tasks touch the same files or protos.

**Still needs:**
- Day-to-day use of the driven lead so far is with Claude Code; a Codex driven lead is covered by tests against recorded streams and not tried on a live run yet.

## Questions read at a glance, keep their history, and investigators search the web

A check, a measure, a log or a CI result is never asked of you: the worker runs it itself, or says in its final note what remains to verify, and the Djinn sends it to a task or to the watcher of the pull request. A question is reserved for a decision or a move only you can make (push a tag, merge a pull request, check something on a Mac). Every question's context puts the commands you must run in a single `~~~`-fenced code block at the top, each preceded by a `#` comment saying what it prints and what to expect, followed by a one-line why, verified facts, and the options with their costs; `djinn question ask` and `djinn question revise` warn whenever a context breaks this shape.

Clicking an option or pressing Space or Enter on it selects it without sending the answer by accident; **Rub the lamp**, Enter in the note field, or Ctrl/Cmd+Enter sends the answer, and answering from the keyboard animates the button it presses.

When you click **Enlighten me**, Djinn snapshots the initial question (Tour 0) and every revision round, automatically appending the history of earlier versions at the bottom of the question whenever an investigator revises it, and anchoring the investigator to the initial question's subject. Investigator workers now inherit the project's configured model when no separate `question_model` is set, can search and fetch the web (`WebSearch` and `WebFetch` on Claude Code, `search_web` and `read_url` on Antigravity, `networkAccess` on Codex), have expanded read-only `git` (`branch`, `rev-parse`, `ls-tree`) and `djinn` (`wish brief`, `task list`, `task get`, `question list`, `block list`, `tilasm list`, `tilasm get`, `question revise`) permissions, and can pass complex Markdown contexts through `djinn question revise --context-file <path>`. A revised question leaves **Being investigated** at once, and an **Enlighten me** request never waits forever behind a start that hangs or ends without a follow-up.

**Still needs:**
- Web search and model inheritance in question investigators are verified by tests across all three providers and in live use on Linux; not checked yet by hand on macOS and Windows.

## The flying carpet and the Hourglass

The overview of every active wish, at the top of the side panel, is now the **flying carpet** (*tapis volant* in French), reachable from anywhere with Ctrl+1 (Cmd+1 on macOS). Live machine and worker metrics now have their own home in the side panel, **the Hourglass** (Ctrl+2 / Cmd+2 on macOS): machine CPU and memory over time, each running worker's graphs, and where command gate time goes.

Each notch of the operating load bar now shows the exact number of workers the scheduler lets run there given the machine's memory and slot limits. Task cards and rows show a task's model turns over its whole life beside its current run against the limit (`142 turns (37/500)`), and an azima can be renamed from its card or with `djinn task update --title`.

## Branches, pull requests, and watchers

Answering yes to Djinn's pull request question now opens the pull or merge request as a draft itself—reusing an existing one, starting a worker when the project defines an `open-pr` or `open-mr` skill, or running `gh pr create --draft` or `glab mr create --draft` directly—or tells the Djinn when the move is still yours to make. Naming an azima's branch or a wish's integration branch after a remote branch fetches it first and cuts the local branch from it; if a branch is behind or diverged from its remote, Djinn holds merges and pushes instead of overwriting remote work.

Watchers run the commands declared by their project's skills in addition to those a developer allows, with `$DJINN_HOME`, `$DJINN_TASK_ID` and `$DJINN_WISH_ID` expanded and their working folder created before start. Refused worker tool calls go to the Djinn alone without raising a warning banner in the window; when a worker genuinely needs a new right, the Djinn asks you through a question.

**Still needs:**
- Opening a draft merge request from a question and remote branch tracking are covered by tests; not checked yet end to end on a live GitLab repository.

## Nothing Djinn started outlives it

Killing Djinn leaves nothing running behind it: its workers, watchers and checks, and the commands a worker runs under a gate, die with it. On Linux the kernel kills each worker at once; on Linux and macOS a small shell of Djinn's stops what they started; on Windows a job object kills them all. Should one survive all the same, the next start stops it before it resumes any task, and tells the Djinn which ones it stopped. Djinn never touches a process it did not start: it records each one it starts in `run/` of its data folder, with its start time, so a later process that reuses the same number is left alone.

**Still needs:**
- Covered by tests on Linux, macOS and Windows in continuous integration; not checked yet by hand on macOS and Windows.

## Errors and crashes land in the log, with their stack

An error in one of Djinn's loops (the scheduler, the integration, the pushes, the watchers) is logged in `logs/djinn.log` with which loop and which task or wish, and an internal error of its server with its whole message. A panic in a call to the server, or in the window, is logged with its stack and Djinn goes on. A crash leaves `crash.txt`, what Djinn died of; the next start renames it `crash-<time>.txt`, logs it, and keeps the last 5. Send the latest one with `djinn.log` when you report a crash. Commands that succeed within a second are logged only at `DJINN_LOG=debug`, so the log keeps what matters.

**Still needs:**
- Not checked yet by hand on macOS and Windows.

## Updates follow your line of work, and can install by themselves

For those who build Djinn from a checkout: when a wish moves its work to a new branch cut from the one Djinn runs, the update banner shows its builds on the running line, "of feat/robustness, continuing feat/wails-go", instead of folding them among other branches'. With `install: true` in a project's settings, builds of your own branch line install by themselves as they complete, and an install that stalls times out instead of spinning forever.

## Under the hood

- Djinn runs fewer Git commands to integrate and push work, and its tests spawn fewer processes, which keeps the Windows continuous integration within its time limits.
- [docs/pitfalls.md](https://github.com/Empowill/Djinn/blob/main/docs/pitfalls.md) documents the codebase's known traps and how to spot them.
- A test that left a goroutine running could end the whole test run with no failing test named; such runs now name the tests left running.

## Fixed

- `djinn up` could deadlock when acquiring command gates under the harness lock; gate calls and resource measurements now run outside the lock, and a watchdog logs slow locks.
- Answering a question could send the answer more than once to the lead or leave the question card unupdated.
- A pull request could be watched twice when the lead had already started a watcher on it by hand: Djinn's own babysit now adopts that watcher instead of starting another.
- The window kept repainting while nothing changed and kept the stream events of closed task cards in memory.
- A worker sampled right at process start could report `0 B` of memory instead of no reading yet.

## Upgrading from v0.1.1

Nothing to do: your data folder is kept as it is. An upgrade from a running terminal lead switches to the driven lead cleanly—the lead terminal is dropped, the window keeps the wish it showed, no waiting event is lost, and the journal starts with the next batch. To go back to the terminal lead, set `"leadDriven": false` in `settings.json` in Djinn's data folder. Djinn adds a `run/` folder to its data folder while it runs; leave it out of your backups, as the socket and the logs.
