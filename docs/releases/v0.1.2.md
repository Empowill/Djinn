# Djinn v0.1.2 (unreleased)

v0.1.2 makes Djinn tidier when it ends and clearer when it fails: nothing it started outlives it, and an error or a crash lands in its log with what you need to report it. The overview of every active wish is renamed the flying carpet, and agents no longer ask you to check what they can check themselves.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. A *lead* agent splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.1.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.0) describe all it does.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

## Nothing Djinn started outlives it

Killing Djinn leaves nothing running behind it: its workers, watchers and checks, and the commands a worker runs under a gate, die with it. On Linux the kernel kills each worker at once; on Linux and macOS a small shell of Djinn's stops what they started; on Windows a job object kills them all. Should one survive all the same, the next start stops it before it resumes any task, and tells the lead which ones it stopped. Djinn never touches a process it did not start: it records each one it starts in `run/` of its data folder, with its start time, so a later process that reuses the same number is left alone.

**Still needs:**
- Covered by tests on Linux, macOS and Windows in continuous integration; not checked yet by hand on macOS and Windows.

## Errors and crashes land in the log, with their stack

An error in one of Djinn's loops (the scheduler, the integration, the pushes, the watchers) is logged in `logs/djinn.log` with which loop and which task or wish, and an internal error of its server with its whole message. A panic in a call to the server, or in the window, is logged with its stack and Djinn goes on. A crash leaves `crash.txt`, what Djinn died of; the next start renames it `crash-<time>.txt`, logs it, and keeps the last 5. Send the latest one with `djinn.log` when you report a crash. Commands that succeed within a second are logged only at `DJINN_LOG=debug`, so the log keeps what matters.

**Still needs:**
- Not checked yet by hand on macOS and Windows.

## The flight plan is renamed the flying carpet

The overview of every active wish, at the top of the side panel, is now the **flying carpet** (*tapis volant* in French), in the window, the user guide and the docs.

## Agents ask you for decisions, not for checks

A check, a measure, a log or a CI result is never asked of you: the worker runs it itself, or says in its final note what remains to verify, and the lead sends it to a task or to the watcher of the pull request. A question is left for a decision or a move only you can make (push a tag, merge a pull request, check something on a Mac), with its exact command in a code block at the top, never in the middle of a sentence.

## Updates follow your line of work

For those who build Djinn from a checkout: when a wish moves its work to a new branch cut from the one Djinn runs, the update banner shows its builds on the running line, "of feat/robustness, continuing feat/wails-go", instead of folding them among other branches'.

## Under the hood

- Djinn runs fewer Git commands to integrate and push work, and its tests spawn fewer processes, which keeps the Windows continuous integration within its time limits.
- A test that left a goroutine running could end the whole test run with no failing test named; such runs now name the tests left running.

## Fixed

- A pull request could be watched twice when the lead had already started a watcher on it by hand: Djinn's own babysit now adopts that watcher instead of starting another.

## Upgrading from v0.1.1

Nothing to do: your data folder is kept as it is. Djinn adds a `run/` folder to it while it runs; leave it out of your backups, as the socket and the logs.
