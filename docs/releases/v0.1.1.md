# Djinn v0.1.1

v0.1.1 is the first release of Djinn you can install: v0.1.0 was published without binaries. It also holds everything done since v0.1.0, two days and more than 600 commits later: Djinn now feels at home on a Mac, one lead serves every wish and talks to you only through questions, workers are kept alive by a watchdog and bound by clear limits, your work lands on the branch you choose, and when something goes wrong Djinn leaves you a log to send.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. A *lead* agent splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.1.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.0) describe all it does.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

## Djinn feels at home on a Mac: a native title bar, a page that makes a wish, and a pill to talk to the lead

Clément Fauvelle ported Djinn to his Mac and redesigned how it looks. The window has a native macOS title bar with its controls in place, a toolbar, and a side panel that folds into a rail of icons and glides open. One header on every page holds the operating load gauge, **Pause** and **Lead**. **New wish** opens a creation page over an animated smoke backdrop in Djinn's colours. A floating pill at the bottom of a wish, **Write to the lead** (Cmd/Ctrl+I), sends the lead a message about that wish, as `djinn lead tell` does from a terminal. Buttons show tooltips with their keyboard shortcuts, and the window drags and zooms like a native one.

On macOS, changes now show live in the window (measured on a Mac: the native end-to-end test failed 5 runs in 6 before, passed 13 in 13 after), system notifications show again for everything that waits for you, and Djinn holds new workers when macOS reports memory pressure (with **Start anyway** to override it for one task).

**Still needs:**
- Not checked yet by hand on a Mac from this release's archives: the title bar, `Djinn.app` opened from the Finder (Dock, Launchpad, notifications of an unsigned app), the agents found when it starts from the Finder.
- Holding workers on memory pressure is covered by unit tests only.
- The macOS build is not signed nor notarized.

## Djinn finds your agents, and sets them up from the window

**Connections & preferences** shows, one line per agent (Claude Code, Codex, Antigravity), whether Djinn finds it, its version, and whether it is signed in, with a button that installs it or signs it in through the agent's own command, in a terminal of the window. It opens by itself when no agent is ready. Djinn looks where your terminal would: its own `PATH`, your login shell's, and the installers' folders, so an agent installed with `npm` or `nvm` is found even when Djinn starts from the Finder. On Windows, the install buttons run the agents' PowerShell installers.

**Still needs:**
- Antigravity has no command that says whether it is signed in: its line shows "unknown".
- Not checked yet by hand on macOS from the Finder, nor on Windows.

## One lead for every wish, and everything it needs from you is a question

Djinn now runs a single lead for all your active wishes, instead of one per wish: one session that sees every wish, so it spots duplicate or conflicting work, and one terminal. **Lead** at the top of a wish opens it focused on that wish; the arrow beside it picks the agent (Claude Code, Codex or Antigravity). The lead starts from `djinn brief`, a summary of every active wish written by Djinn, not by a model.

The lead says nothing for you in its terminal: a report, a "done", a doubt, everything comes as a question in the wish concerned, and it withdraws a question once it is moot. When work leaves a move only you can make (push a tag, merge a pull request, check something on a Mac), the question gives the exact command. Your answers go to the lead, which turns them into tasks itself; **Enlighten me** still sends an investigator worker to dig first. A question can be moved to another wish or withdrawn, and answered from the keyboard: Enter answers, Shift+Enter makes a new line, Ctrl+Shift+Enter (Cmd+Shift+Enter on macOS) enlightens.

Djinn hands the lead what it must act on (a task that ended or failed, a real merge, an answer) in one batch through `djinn lead watch`, and never types into the lead's terminal while you type there or while it shows a choice. When the agent asks for your approval in its terminal (a command to run, a folder to trust), the choice shows at the top of every wish with its options as buttons. A lead that could not start, or ended, shows a dot on **Lead** with the error.

**Still needs:**
- Day-to-day use so far is with a Claude Code lead. Codex is tested against hand-written streams only: Djinn has not run a real Codex yet, as a lead or as a worker.

## The Lamplighter keeps workers going, and every task has its seal

A watchdog, the Lamplighter, watches every worker. A worker silent for 15 minutes with nothing busy, whose stream goes idle or whose process is lost, is ended and continued on its own session; only after three wakes in a row does its task fail, and the lead is told why. Watchers (tasks that run a command with no agent, such as following a pull request) are supervised apart: never ended for being quiet, restarted when their command dies.

A task's *seal* is the set of limits Djinn gives its worker: 2 hours of work in total, 500 model turns per run (shown live, `37/500`), its spending cap, what it may edit and run. A useless task can be cancelled (`djinn task cancel`): its worker stops, its work is never merged, and it shows as **Cancelled**. A restart of Djinn no longer counts against a task's resumes, and a failure caused by the environment rather than the work is replayed instead of left failed.

**Still needs:**
- Codex reports no model turns: its tasks have no turn count.

## Your work lands where you choose: one branch per wish or per azima, pushed when you say

The lead's plan is made of *azimas*: parts of the plan (coded `T01`, `T02`…) that tasks belong to. Each wish now chooses its push strategy: **Per wish**, one branch for the whole wish, or **Per azima**, one branch per azima cut from main, with a pull request Djinn proposes from the azima's goal and keeps up to date. An azima's branch can be named after your team's convention (`djinn task update T07 --branch …`). A chip beside the strategy says where the work lands, and a click changes the wish's branch.

Each project chooses when Djinn pushes: **Standard** (at an azima's end, or after an hour and three tasks) or **On demand**, with a **Push** button. The project lists each branch out of sync with its remote (`↑2 ↓1`), and a push shows its checks as they run. Red push checks start a correction worker at once; you are asked only if it fails. A finished task whose work is not merged yet reads **Merging**, not Done.

A project that names no checks now gets its finished work merged into the wish's own branch (never into main), and a task left out says why. Djinn merges and commits as you, with Git's own `user.name` and `user.email`: on a machine without them, it says which `git config` to run instead of reporting a false conflict. No worker can `git push`, whatever the command or the agent: Djinn starts every worker with a Git setting that makes the push fail, and pushes itself.

**Still needs:**
- Not checked yet with GitLab merge requests per azima.

## Review what the workers merged: a Review tab, whole diffs, comments on a line

Each task's card has **See the diff**: the files it changed, then each file's diff, coloured, unified or side by side. A file past 2,000 lines loads in chunks instead of being cut. A comment on a line of a running task's diff reaches its worker; on a finished task, it becomes a correction task. A **Review** tab per wish lists its merged work, one line per task; tick a task once you have reviewed it, and the lead sees it.

## Tell Djinn how much of your machine it may use

An operating load slider, at the top of the window or `djinn load set`, sets how much of the machine Djinn takes: **Minimal** (20 %), **Medium** (50 %), **High** (80 %), **Max** (100 %) and **Overclock** (150 %), each a share of what the machine allows, or **Auto**, which drops to Minimal as soon as you type or the machine gets busy, and climbs back when you are away. A change acts at once on running workers: at the two lowest notches they run at a lower CPU priority, and extra workers pause (in Auto, Djinn only starts fewer). The gauge forecasts CPU and memory, from each worker's measured peak. An optional memory guard caps each worker at a multiple of its agent's observed peak (`djinn up --worker-memory-guard 2.5`, on Linux with systemd's cgroup v2).

**Still needs:**
- Auto follows the session's idle time where the desktop gives it; elsewhere (SSH, a desktop that gives none), the load of other programs only.
- On Windows, workers cannot be paused and their CPU and memory are not measured yet.

## A wish reads at a glance

Task rows read on two lines: the status first, the code and full title, then the project, the agent and model, the real working time, turns, tokens and one price (reported and estimated on hover). The **Tasks** tab can also show the whole wish as a tree, oldest at the bottom. Azimas read as one list in a stable order, what moves first; an opened azima shows its description beside its parts. The lead can keep work for later as **Draft** azimas, opened when their time comes or moved to another wish. Wishes can be renamed. Under the overview, a resources panel charts each running worker's CPU and memory, with the commands each project ran and their gate time.

The window stays fast on large wishes: only the tab shown loads, lists come 50 at a time, and a long task list renders within a measured budget.

## Every pull or merge request a task opens is watched

A project names its babysit skill (`metadata.djinn.babysit` in a skill's `SKILL.md`). When a task opens a pull request (`gh pr create`) or a merge request (`glab mr create`), Djinn starts a watcher on it at once, in the same wish: each failed pipeline, comment or conflict wakes the lead, which follows the skill, until the request is merged. `babysit: false` in the project's settings turns it off.

**Still needs:**
- Not checked yet end to end on a live GitLab merge request until it merges.

## When Djinn is stuck, it leaves you what to send: logs and a dump

Djinn logs what it does in `logs/` of its data folder: every call to its server, every command it runs (Git, `gh`, your checks) with its duration and exit code, every worker started and ended. The log never holds a prompt, a message or a secret, and rolls over at 10 MB, 50 MB at most, on every system. When Djinn freezes, `djinn debug dump` writes where each part of it waits, even when its server no longer answers. A stop that hangs dumps by itself, then exits after 30 seconds instead of hanging.

**Still needs:**
- The logs, the dump and the stop watchdog are not checked yet by hand on macOS and Windows, only by their continuous integration (on Windows, where there is no signal, `djinn debug dump` asks through a file).

## Antigravity workers pick up where they left off, and the lead can hand a task to another agent

A resumed Antigravity worker or lead continues its own conversation instead of starting over, reads what it needs outside its worktree, may read web pages, and a model error after its work was committed no longer fails the task. The lead can change a task's agent and model in one command (`djinn task set-agent`) without making a new task.

## Updates say what changed

When a newer Djinn is available, a banner offers **Update** with its release notes; nothing restarts without your click, and × hides it until a newer one comes. For those who build Djinn from a checkout, the banner names each build (its commit, branch and wish) and lists the tasks it adds.

**Still needs:**
- Not checked yet: an update from inside the app from this release to the next one.

## Every release ships ready-made binaries for each target

Linux (amd64 and arm64, GTK 3, GTK 4 as an experiment, and a browser build), macOS (one universal binary, and `Djinn.app`) and Windows (amd64 and arm64). Each release attaches `SHA256SUMS`, `LICENSE`, `NOTICE`, the third-party notices and the install scripts. A dry run builds and checks every target from any branch without publishing.

**Still needs:**
- Not checked yet on physical Windows hardware (the window, SmartScreen) or arm64 Linux hardware.
- `go install github.com/empowill/djinn/cmd/djinn@v0.1.1` works only if the tag carries the built interface; the install scripts need it only on a system no archive fits.

## Under the hood

- Continuous integration runs Djinn's Go tests on Linux, macOS and Windows, and the interface and end-to-end tests on Linux and Windows. The Windows job does not block a change yet: it has been green, not yet steadily.
- Tests never call a paid model and never touch your real Djinn data; a test slower than 10 seconds fails.

## Fixed

- `djinn up` could stop answering its command line for minutes under load; a task list no longer reads every event, and every Git command has a deadline.
- The window could run out of connections and stop updating, or re-read every task at each worker measurement.
- A task could start before the work it depends on was merged.
- A push could wait forever on a correction or a question that was cleared, withdrawn or stopped; a red push check no longer turns committed tasks back to conflict.
- After an update, old finished work could be queued for merging again.
- Keeping a branch up with main could stall on a tag that clashed with the remote's.
- Answering a question could start an install or a release Djinn had not asked about in that question.
- A task's turn budget (50) was too small for real work: it is 500.
- Overclock ran fewer workers than the machine could hold.
- An azima could show done while one of its parts still ran, and its counters were wrong until every task was loaded.
- The lead could find a line typed by Djinn in its prompt box.
- A pull request watcher stayed silent after a restart when a new push failed the same check.
- An unknown field in a project's settings stopped Djinn; it now warns and goes on.
- A wish with no project hid its tasks.
- Deleting a task that others depend on is refused.

## Upgrading from v0.1.0

v0.1.0 had no binaries: install v0.1.1 with the command above. Your data folder is kept as it is.

- The first start keeps the lead of your first active wish as the one lead; the other wishes' leads are no longer started.
- Warm workers are gone: `djinn up --warm-workers` is no longer accepted.
- The project setting `question_workers` is gone: answers go to the lead, and `enlighten_workers: false` lets the lead investigate itself instead of an investigator worker. A setting Djinn does not know is reported and ignored.
- Djinn needs Git's `user.name` and `user.email` to merge work: set them if `git config user.name` prints nothing.
