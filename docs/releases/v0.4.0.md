# Djinn v0.4.0

v0.4.0 is a large release after v0.3.0. Djinn now runs its workers on several Claude accounts, in an order you set, and moves a task to another account when one hits its limit; every command a Claude worker runs takes its turn on the machine, and a memory brake freezes what escapes the turns before the machine runs out of memory; the Hourglass gains a Gates tab and a Statistics tab; the window can be driven from the keyboard and stays fluid under load; after a crash Djinn resumes no worker until it knows why. Investigations can now search the web, a project describes itself to Djinn in a `djinn.yaml`, and under the one-branch-per-azima strategy Djinn opens each azima's draft pull request by itself.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. One *Djinn*, the lead agent, splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.2.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.2.0) describe the last large release before this one, and [v0.1.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.0) what Djinn is built on.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

## Several Claude accounts, in the order you choose

With two Claude subscriptions on one machine, Djinn now runs its workers on both. The **Summoning Circle**, a new page below the Grimoire in the side panel, lists the agents, then every sign-in under **Accounts · order of priority**: add a Claude Code account there, sign in to it in the panel's terminal, and drag the lines (or press Alt+Up and Alt+Down) to rank them. By default Djinn picks, for each new task, the sign-in whose week ends soonest, since what is left of a week is lost at its reset; **Manual order** follows your ranking instead. Each line shows its week's and its 5 hours' gauges with when each ends, the workers running there and the tasks waiting for its limit. A worker that hits its account's limit moves at once to another sign-in, its session copied there; when every sign-in is full, a task may overflow on extra credits if the account allows it. You can pause an account, mark one unlimited, and pin the Djinn itself on one account. The Summoning Circle is also now the one place to choose the Djinn's agent, model and account, and a window that opens with no agent able to lead opens on it. The same moves exist on the command line (`djinn lead accounts`, `djinn lead add-account`, `djinn lead order`, `djinn lead pin`, `djinn lead pause-account`). See [Several Claude accounts](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/several-claude-accounts.md).

**Still needs:**
- Quotas are read for Claude Code only; Codex accounts are listed and ordered but their quota is not read.
- Covered by tests with fake agents; the move of a session from one account to another has not been checked on macOS or Windows by hand.

## Every command takes its turn on the machine

The gates used to hold only the commands that named one. Now every command a Claude worker runs that neither reads nor edits files is admitted: it waits only while the machine is under pressure or lacks the memory the command needed before, then runs exactly as written. Djinn measures each command and recognises it again in another task and another folder; a command measured heavy (past 2 GiB of memory or a minute of CPU) runs one at a time across the machine, while light ones share a gate's name. A gate is never taken back from a command that still runs: when a command holds its gate far past its usual time, the Djinn is told once, and nothing is cut. The history of gates and admissions is kept for a week, across restarts. You may now pause a worker whose light command only shares a gate. See [Gates](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/gates.md).

**Still needs:**
- Admission applies to Claude Code workers; a command of another agent, or of your terminal, that names no gate is not held back.

## A memory brake for what escapes the gates

A process a command left running, or the sum of the workers, could still fill the machine's memory. Under 5 % of memory available, or when tasks keep waiting for memory, Djinn now freezes the worker whose memory grew most outside any gate, with its containers; if the memory stays short 30 seconds, that worker is interrupted, and it resumes in its session once the memory is calm. A command a gate admitted is never interrupted. You choose the percent, or Off, at the end of the Summoning Circle; it applies at once. The Docker containers a worker starts are now tied to its task, removed when it ends, and bounded against a runaway (by default 4 GiB of memory and 1024 processes each), limits a project raises in its `djinn.yaml`. See [Machine and load](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/machine-and-load.md).

**Still needs:**
- Freezing and interrupting a real Claude worker under a memory ballast was tried on Linux; not tried on macOS or Windows.

## The Hourglass: a Gates tab and a Statistics tab

The Hourglass now has three large tabs: **Machine**, **Gates** and **Statistics**. **Gates** shows who holds each gate and who waits, the gates held in the last hour, and each command admitted with what it cost and how long it waited. **Statistics** reads what the work has been, over 7 days, 30 days or all: tasks created by day or week and by type, the median and 90th percentile of how long tasks waited, ran, were held by a gate or paused, how long your answers took, and the size of first prompts, filtered by project. The same tables are open to you and to the agents: `djinn query` prints any list Djinn keeps (tasks, questions, wishes, projects) with chosen columns, filters, groups and measures, as text or CSV, and an agent reaches it through MCP. A query only reads. See [Queries](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/queries.md) and [The window](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/the-window.md).

**Still needs:**
- Its speed was measured on a copy of a real database on Linux only.

## Drive the window from the keyboard

Up and Down move between a question's options, Left and Right from one question to the next across wishes, and the keys answer it; Ctrl+Up and Ctrl+Down go to the wish above or below; Alt+Left and Alt+Right (Cmd+[ and Cmd+] on macOS) go back and forward between views as in a browser, even with the focus inside a tilasm (a page that explains a wish). Typing in **Write to the Djinn**, in a new wish or in a tilasm comment no longer redraws the page at each key, and the workers and checks now run at a lower CPU priority than the window, so typing stays fluid on a loaded machine. On macOS, Cmd+A selects all on a French keyboard instead of quitting, Cmd+H hides Djinn again, and the Edit and Window menus are complete. See [The window](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/the-window.md).

**Still needs:**
- The keyboard shortcuts are covered by end-to-end tests in Chromium; not checked by hand on Windows.

## After a crash, Djinn resumes no worker by itself

In October 2026 a worker's container ran a fork bomb and took the machine down; the next start resumed every worker, that one too. Now, after a stop that was not clean (a crash, a kill, the machine going down) or when memory was at 90 % or more just before the stop, the next start leaves the workers interrupted, worktree and session kept, and says why in a banner and to the Djinn, which continues each one that may go on. `djinn up --paused` does the same on demand. A run cut by such a stop also no longer counts the time Djinn was down against a worker's time budget. See [Restarts and updates](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/restarts-and-updates.md).

**Still needs:**
- Covered by tests that simulate each kind of stop; a real crash on macOS or Windows has not been tried.

## Investigations search the web

An investigation task now searches and reads web pages as a question's investigator already did, even in a project whose permissions keep the network off; its commands stay the project's, so a command that reaches the network is still refused, and a work task gets neither. See [Investigation](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/investigation.md).

**Still needs:**
- Covered by tests of the permissions given to each agent; not yet seen in a real investigation on Codex or Antigravity.

## A project describes itself in djinn.yaml

A repository can now hold a `djinn.yaml`, at its root or in its agents folder, read on the reference branch so a worker never changes what bounds it. Today it holds the ceilings of the containers. A file Djinn cannot read shows under **To fix** in the project's configuration with the error, and Djinn's defaults hold; an unknown field is ignored with a quieter warning. See [Project and settings](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/project-and-settings.md).

## Pull requests per azima, opened by Djinn

Under the one-branch-per-azima push strategy (an *azima* is a part of the Djinn's plan), Djinn now opens an azima's pull request as a draft at its branch's first push, with no question, through the project's skill when it has one. Work started from an azima's branch, or with no azima, lands on an azima of its own, and the Djinn never pushes to `main`. A red push check, or the correction repairing a branch, now holds only that azima's tasks. When a pull request watcher reports a conflict, the Djinn gets a task to resolve it in the same pass. See [Push strategy](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/push-strategy.md) and [Pull requests](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/pull-requests.md).

**Still needs:**
- Covered by tests against a fake forge and recorded answers of `gh` and `glab`; not yet checked on a live GitLab project.

## Tilasms and questions settle each other

When an open question links a tilasm, **Launch** on the tilasm answers the question with its recommended option, and answering the question sends the comments you left in draft on the tilasm with your answer. A question that cites a tilasm by its code now stores a working link, which opens in the window. See [Tilasm](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/tilasm.md).

## Under the hood

- New dependencies for the charts and the tables: Apache ECharts (with ZRender) and Apache Arrow for JavaScript in the window, loaded only when needed, and Apache Arrow for Go behind `djinn query`; all listed in the third-party notices.
- The command line reads the files it is given (`--context-file`, `--prompt-file`, `--plan-file`) itself, and a refused call names the flag and the values that fit; every task stores its kind (work, correction, review, watcher...) from its creation.
- The tests are steadier on a loaded Mac and on Windows.

## Fixed

- The Djinn's message bubble above **Write to the Djinn** is now one sentence, an acknowledgement, that fades after 2 minutes instead of staying.
- On macOS, Djinn now reads used memory as Activity Monitor does, compressed memory included, and sizes the worker slots on what workers were measured to peak at rather than a fixed default: a loaded Mac no longer starts workers into its compressor, and a Mac with room runs more than one.
- Merging `main` into a wish's or an azima's pushed branch now makes its push due, instead of leaving the merge unpushed.
- A task's branch rewritten by a forced push is followed, and a branch the remote deleted no longer lingers in Djinn's view.
- A worker cut by a network outage while it ended on its error is no longer paused; it resumes when the network is back.
- A question put off is placed after the wish's last question, even when two come at the same instant; a wish's history keeps the journal's order in that case too.
- Grouping the Statistics tab by week no longer blanks the window.

## Upgrading from v0.3.0

Nothing to do: your data folder, wishes, settings and lead journal are kept, and each stored task gets its kind at the first start. A few things behave differently:
- The memory brake is on, at 5 %. On a laptop where a browser leaves Djinn little room, lower it to 3 % or turn it Off at the end of the Summoning Circle.
- Workers and Djinn's checks run at a lower CPU priority than the window at every load level but Overclock; they still use all the CPU nothing else asks for.
- On macOS, Djinn counts memory more strictly than v0.3.0 and may start fewer workers on a Mac under memory pressure.
- The Djinn's agent, model and account are chosen in the Summoning Circle only: the selector at the top of a wish is gone.
- After an unclean stop, interrupted workers wait for the Djinn to continue them instead of resuming at once.
