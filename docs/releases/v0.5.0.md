# Djinn v0.5.0

v0.5.0 follows v0.4.0 by a week. A project now declares its own gates and its team's settings in one versioned `.agents/djinn.yaml`, and its settings open as a page of the window in tabs; the Hourglass's Gates tab says, gate by gate, who held whom and how long; Djinn frees the folders of finished tasks by itself; on a Mac, macOS's own memory pressure decides what runs; a file pasted into **Write to the Djinn** goes with the message; and Djinn refuses to push a project's reference branch or a protected one. The repository is also ready for outside contributors: a security policy, a code of conduct, issue forms.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. One *Djinn*, the lead agent, splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.4.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.4.0) and [v0.2.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.2.0) describe the last large releases before this one.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

**Still needs:**
- The Linux builds for GTK 4 (WebKitGTK 6.0) are built by the release workflow, which does not wait for them; nobody has opened this release's GTK 4 build yet.
- This release's `Djinn.app` is built and checked by the release workflow; that it opens on a Mac is not checked there.

## Gates a project declares, and a Gates tab that says who waited for whom

A project can now declare its own gates in its `.agents/djinn.yaml`: the commands that rebuild what the workers share (a stack, its images) hold the gate alone, and the commands that use it share it, never while one holds it alone. A developer who clones the repository gets the same gates with nothing to set, and a gate is the project's own (`stack@app`), read on the reference branch so a worker never changes what bounds it. `djinn project gates` shows the gates as Djinn applies them, first saying the file and the commit it read them on, and turns one off or on in your own settings only. Djinn's own repository declares its gates this way, and its developers work under them every day.

Every wait is now explained. A worker whose command waited reads, beside its result, each holder it waited for in turn and how long; the Hourglass's **Gates** tab groups the gates by project, shows each one as a seal (free, held, with a flame for each worker waiting), draws one lane per gate over the last hour, 6 hours or day with what each request waited for under the pointer, and keeps this history three months instead of a week, across restarts. Gates go to the worker of the wish you ranked first, then second, then third.

A cost learned wrong no longer holds a worker: a command alone goes whatever its peak, a peak counts for half the machine's memory at most, a command waits for memory five minutes at most, and the gates hold a command to its usual peak over its last 20 runs, a lone peak far above the others left out. `djinn command forget` forgets a cost by command, by the words it starts with, or for a whole project. `admit: false` under `gates_options:` in `djinn.yaml` turns the admissions off for a project's workers. See [Gates](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/gates.md).

**Still needs:**
- Seen in daily use on Linux; on macOS only by a launch test on a CI runner, not yet on a Mac under a day of real work.

## The team's settings in djinn.yaml, a project's settings in one page

A repository's shared settings for its workers (agent, model, budget, checks, push cadence...) now live under `settings:` in `.agents/djinn.yaml`, next to its gates and its container ceilings; the file carries the version of its schema (`version: 1`), and a newer one than this Djinn knows is refused whole rather than read wrong. `.agents/settings.txtpb` is no longer read. Djinn's own repository moved to this file and runs on it.

A click on a project now opens its settings as a page of the window, in tabs (General, Worker defaults, Gates and checks, Integration and push, Workers' brief, Skills, Permissions, Changes on main), and each setting shows the repository's value, yours, and the one Djinn keeps. What the workers are told can now be set by kind of task (work, investigation, mockup, ifrit, or a general text), in three layers: the Summoning Circle's new **Workers' instructions** tab for this machine, the repository's `djinn.yaml` for the team, your own file for you. To try a change of the configuration before it merges, `djinn project set-branch` with its config flag makes your Djinn read `djinn.yaml` and the skills on a branch you name; the permissions stay read on the reference branch, and once the branch is merged and deleted, Djinn reads the reference branch again by itself. See [Project and settings](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/project-and-settings.md).

**Still needs:**
- The configuration branch is covered by tests against a local remote; not yet tried by a team on a live forge.

## Djinn frees the disk by itself

Worktrees no longer fill the disk week after week. A task done with its work merged, or with nothing to merge (an investigation, a mockup), has its worktree and scratch folder freed 30 days after it ended; once its azima (a part of the Djinn's plan) is validated or its wish granted, its worktree, scratch folder and local branch go at once. Djinn never loses work: a worktree with changes not committed stays, and so does a local branch with commits found neither in the integration branch nor on the remote; a remote branch is never touched. A granted wish shows its cleanup in a band under its header, azima by azima, with what was freed or kept and why. A freed task can still be forked from its conversation. The Hourglass's **Disk** tab now measures the disk's real sources, leaves little unmeasured, says when it measured with a button to measure again, and sums what finished tasks hold and when Djinn will free it. See [Task and worker](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/task-and-worker.md) and [Machine and load](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/machine-and-load.md).

**Still needs:**
- Seen freeing the branches of validated azimas on Linux; not checked on macOS or Windows.

## On a Mac, macOS decides the pressure

macOS compresses, then swaps, rather than refuse memory, and always shows little free; a busy Mac can show a load of 32 on 3 cores with most of its memory free. Djinn now leaves the pressure to macOS: neither the load nor the free memory holds a new worker or a gate there, only macOS's critical memory pressure does, and a heavy command waits a bounded time at its warning level. The share of the cores sets the workers (on a 10-core Mac, 3 on Medium, 5 on Max), and a command's peak is what its largest process really held, compressed memory included, as Activity Monitor counts it. See [Machine and load](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/machine-and-load.md).

**Still needs:**
- A launch test on a macOS CI runner starts Djinn, admits a task and runs a command under a gate; not yet checked on a 16 GB Mac over a day of real load (swap used, time at warning).

## Paste files into Write to the Djinn

Paste a screenshot or a file into **Write to the Djinn** (Ctrl+V, Cmd+V on a Mac): it becomes a chip above your text, a thumbnail for an image, removable before you send; up to 10 files of 20 MB each go with one message, even without a word. Djinn keeps each file in the wish and names it to the Djinn, which opens it and hands it to a worker that needs it. `djinn lead tell` takes the same files. See [The window](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/the-window.md).

**Still needs:**
- Tried with a real paste in the Linux window; not checked on macOS or Windows.

## Djinn never pushes a protected branch

Djinn now refuses to push a project's reference branch (`main` on most projects) or a branch its forge protects, whatever the wish and its push strategy, before its push checks run: such a branch reaches the remote only through a merged pull or merge request. A forge's protection does not stop an admin's token, which is why Djinn refuses these pushes itself. The branch's line says why and gives the command that gives the wish a branch of its own; the work stays merged and checked in your local branch. See [Push](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/push.md).

**Still needs:**
- Covered by tests; the protected branches of a live GitLab project have not been read yet.

## A question holds the work that waits for its answer

When the Djinn needs a precision before it can start some work, the question now holds that work, a planned task or an azima not started: it waits for your answer as for a dependency, the question shows **Blocks** with what it holds, and your answer, or a withdrawal, releases it. See [Question and move](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/question-and-move.md).

## One Djinn per data folder, a start that does not stop

`djinn up` now locks its data folder before it writes anything there: a second `djinn up` on the same folder brings the first window to the front and ends, or, when the first does not answer, ends at once with its data untouched. `djinn backup restore` refuses a folder a running Djinn holds. A part of the database that fails to migrate at start is now a warning: Djinn starts, only that part is missing, and the next start tries again. A database written by a newer Djinn opens with a warning instead of a refusal, so going back a version never forces a reinstall. Djinn's local settings migrate at start too, each change once. See [Restarts and updates](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/restarts-and-updates.md).

## Djinn fetches less, at your pace

Djinn fetches only what its work needs and shares each fetch between the watch, the merge of main and the workers' starts. Once you have touched nothing for fifteen minutes and no worker runs, it looks every hour; it looks at once when you come back. A worker never starts from a stale branch. See [Project and settings](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/project-and-settings.md).

## A window that tells you more

The version of the running Djinn now shows at the foot of the side panel's menu, and under the **EARLY ACCESS** tag: give it in a bug report. **To fix** counts the things to fix alone, as the gear and the inbox do. When Claude Code cannot keep a worker's session (a folder name too long for an encrypted home on Linux), the worker's start line says so and the project lists it under **To fix**. On Linux, a window stuck on its loader, its page silent 3 seconds after loading, is now probed, logged and loaded again once, silently. See [The window](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/the-window.md).

**Still needs:**
- The silent-page reload is covered by tests of the native window on Linux; not yet seen recovering a real stuck window.

## Ready for outside contributors

The repository now has a [security policy](https://github.com/Empowill/Djinn/blob/main/SECURITY.md) (report a flaw privately, never in a public issue), a [code of conduct](https://github.com/Empowill/Djinn/blob/main/CODE_OF_CONDUCT.md), issue forms that ask for the version, the system and the logs, and a rewritten README. **Report a bug**, at the top of the Grimoire, opens the bug form in your browser. The user guide says [what leaves your machine](https://github.com/Empowill/Djinn/blob/main/docs/user-guide.md#what-leaves-your-machine): no telemetry, no crash report, and `djinn up --update-check=false` (or `DJINN_UPDATE_CHECK=off`) asks no server for a newer release.

## Under the hood

- No new dependency. `npm audit` reports no vulnerability: Vite, Zod and a few others moved to patched releases within their ranges.
- The commit check and CI refuse a change of the API's protos that breaks compatibility with the reference branch; the Hourglass's Gates tab and the reads of prompts stay fast on a large database.

## Fixed

- The History tab of a long wish no longer crashes Djinn.
- An inline script given to a command in a here-document no longer makes a light command count as heavy.
- The labels of the Gates tab no longer overlap, and its readout no longer hides under the terminal panel.
- The **EARLY ACCESS** tag no longer overlaps the panel toggle on a window 1300 pixels wide or less.
- A wish whose branch was named but never made no longer waits in silence: Djinn makes the branch before the next merge.
- An azima's card now follows its pull request on the forge, **PR merged** or **PR closed**, even once its branch is gone, and the Djinn is no longer told again about an azima already closed.
- A task refused because it would make one azima wait for another now says what to change.
- **Same as lead** in the Summoning Circle is a model choice of its own: a project's settings no longer pick a model for a row set to it.

## Upgrading from v0.4.0

Your data folder, wishes, settings and lead journal are kept. A few things need you or behave differently:
- A repository's `.agents/settings.txtpb` is no longer read: move its settings under `settings:` in `.agents/djinn.yaml`, then delete it. Until then Djinn's defaults and your own file apply, and the project shows a warning under **To fix**. The permissions stay in `.agents/permissions.txtpb`.
- Your own project files on this machine migrate at the first start: the provider and model lines an older Djinn left there are dropped, since the Summoning Circle chooses every worker's agent and model.
- At its first start, Djinn frees the worktrees and scratch folders of tasks done more than 30 days ago with their work merged, and the folders and local branches of tasks whose azima is validated or wish granted; work not committed or not pushed stays. Fork a freed task to continue it.
- A wish that integrates into the reference branch with no branch of its own is no longer pushed: give it a branch, or choose the per-azima push strategy.
- On macOS, the load and the free memory no longer hold workers or gates; only macOS's critical memory pressure does.
- A second `djinn up` on the same data folder no longer starts a second Djinn.
