# Djinn v0.3.0

v0.3.0 follows v0.2.0 with one new capability and a set of fixes: the Djinn learns to run a bounded improvement loop alone, when you ask for one, and under the one-branch-per-azima push strategy each azima branch now keeps its own push hold, and a repair of its red push checks lands on that branch. Djinn also reads a Mac's available memory as macOS itself does, so a Mac runs as many workers as its CPU allows instead of one; a pull request watcher reports every new comment, including a comment on a line of the diff, and only for the requests it was given; an investigator that falls back to Claude Code can revise its question again; and the load setting, the usage limits and the scheduler no longer disagree for a moment.

Djinn is a local desktop application that turns what you wish into work done by coding agents (Claude Code, Codex, Antigravity) on your own machine, with your own accounts. One *Djinn*, the lead agent, splits each wish into tasks; *workers* do them in their own Git worktrees; Djinn schedules, checks and merges their work, and asks you only what only you can decide. New to Djinn? [v0.2.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.2.0) describe the last large release, and [v0.1.0's notes](https://github.com/Empowill/Djinn/releases/tag/v0.1.0) what Djinn is built on.

## Install

Install Djinn with a single command, no administrator rights or `sudo` needed:

**macOS and Linux:**
```sh
curl -fsSL https://github.com/Empowill/Djinn/releases/latest/download/install.sh | sh
```

**Windows (PowerShell):**
```powershell
irm https://github.com/Empowill/Djinn/releases/latest/download/install.ps1 | iex
```

The script picks the archive for your system, checks it against `SHA256SUMS`, and puts `djinn` in your own folders. On Linux without WebKitGTK it installs a build that opens Djinn in your browser. Then run `djinn up`. Djinn asks for no API key: the work is done by the agents you installed and signed in to.

macOS builds are not signed yet. `install.sh` (through `curl`) is not affected; `Djinn.app` downloaded with a browser must be allowed once in *System Settings › Privacy & Security*, or with `xattr -dr com.apple.quarantine Djinn.app`.

## A bounded improvement loop the Djinn runs alone, when you ask

You can now ask the Djinn, in a message or an answer, to iterate on a piece of work by itself: cycles of "test as a user, then fix", each launched by the Djinn without coming back to you. It opens such a loop only when you ask in so many words, and only once three things are set: its limits (a time, a number of cycles, or both), which it asks you first; a named scope that the fixes stay inside; and a check an agent can run alone (tests, commands, measurable criteria). While the loop runs it asks you no blocking question, says each decision you would want to know, and keeps the cycle count in its journal; at the limit it publishes a summary tilasm (a page that explains the wish) with the scores cycle by cycle and asks you what comes next. It never lifts what Djinn refuses, never opens or merges a pull request, and never pushes a tag on your behalf.

**Still needs:**
- This is guidance built into the Djinn's notes, not a mechanism Djinn enforces: no automated test runs a full loop yet.

## Djinn reads a Mac's memory as macOS does

On macOS, Djinn counted only free pages as available memory, leaving out the file cache and the room macOS makes by compressing memory: a 16 GB Mac under normal pressure read about 95 % used, the **Hourglass**'s memory heatmap stayed at the top, and the memory rule left room for one worker at every load notch, even where the CPU allowed four. Djinn now takes the share of memory the macOS kernel itself reports available, the one its memory pressure follows, and falls back to the page counts, file cache included, when that share is missing. The Hourglass, the worker slots and the command gates all read it alike; the system's own pressure level still holds new workers back. On the Mac that showed the problem, at 42 % available, Djinn now reads about 7.2 GB instead of 2.4 GB.

Checked by hand on macOS (Apple silicon): the Hourglass's memory heatmap compared with Activity Monitor, and `djinn load get` for the slots; the counting itself is covered by tests that run on every system.

**Still needs:**
- Not checked by hand on an Intel Mac yet.

## Pull request watchers that report every comment, and only their own request

When Djinn watches a pull request a task opened, with the project's babysitting skill, the watcher now reports each new comment as its own line with its author and link: comments of the conversation, reviews, and comments on a line of the diff, which it used to miss when they came alone in a review without a body. Each comment is reported once, even after a restart. A watcher also speaks only of the requests it was given: it no longer reports other open pull or merge requests whose branch starts with `djinn/`, which already have their own watcher.

This applies to the babysitting skills of Djinn's own repository (`babysit-pr` for GitHub, `babysit-mr` for GitLab), which a project can summon with `djinn skill summon` or copy; a project with its own skill keeps what its skill says. See [Pull requests](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/pull-requests.md).

**Still needs:**
- The GitLab watcher still reports only the latest comment of each look, not comments on lines of the diff one by one.
- Covered by tests against a fake forge; the line-comment case was met on a real GitHub pull request, the fix not yet seen on one.

## Push repairs stay on the branch they repair

Under the per-azima push strategy (one branch per azima, a part of the Djinn's plan), a correction of an azima branch's red push checks started from that branch but merged its work into the wish's own branch: two such repairs reached `main` and brought it an azima's work whose pull request nobody had reviewed yet. A correction, and a repair of the Djinn's that Djinn adopts, are now part of the azima whose branch is red: their work lands on that branch, never on the wish's branch nor on `main`. A repair aims at the branch that is held, not at the last one pushed, and your answer to a push question (**Push it**, **Not now**, **Push again**) acts on that push alone: it no longer started a correction of another azima's held branch, nor reset its count of red runs.

Each azima branch also keeps its own push hold, with its own correction and its own attempts: another branch going red is held beside it, never in its place; another branch pushing green no longer lifts it, and only its own repair or green push does. The top of the wish shows the hold Djinn acted on last; once it lifts, another branch still held shows there. See [Push](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/push.md).

**Still needs:**
- Covered by tests that reproduce each case; not yet seen on a live wish with several azima branches red at once.

## Under the hood

- The Windows end-to-end tests run on one Playwright worker and wait out a slow runner, and the test timeouts hold under a full local run.
- The Djinn's built-in notes and documentation keep generic examples, nothing from another project.

## Fixed

- An investigator set on Antigravity, which cannot run read-only, ran on Claude Code without a folder to write in and with a context Claude Code refuses: it could not revise its question. It now gets its folder and revises through a context file, as the Djinn's notes and the [Enlighten me](https://github.com/Empowill/Djinn/blob/main/docs/site/pages/enlighten.md) page now say.
- A usage limit whose reset passed while the scheduler was working was judged held, then cleared, and its task resumed without the Djinn hearing that the limit had lifted. The scheduler now reads the time once per pass.
- Changing the load notch while Djinn was sending the load could show one notch with the worker slots of another, and a late automatic change could undo the notch you had just chosen. Two changes at once could also reach the scheduler in the wrong order, leaving it on a notch the slider no longer showed. The notch you chose, the one in effect and the one the scheduler runs now move together.
- A worker could fail at its very start when Djinn cleaned up the project's worktrees at the same moment, for instance beside an integration worktree made again: the cleanup deleted the Git record of the worktree being created. A project's worktree creations and cleanups now take turns.

## Upgrading from v0.2.0

Nothing to do: your data folder, wishes, settings and lead journal are kept as they are, and a push held before the upgrade reads as it was. On macOS, Djinn now sees more memory available and may start more workers and grant command gates sooner than v0.2.0 did; lower the operating load slider if you want fewer.
